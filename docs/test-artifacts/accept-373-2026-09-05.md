## Spec facts learned

1. **Dead/slow swarms must read as item-level, not lane-level.** BitPlay's
   add endpoint *blocks* until metadata arrives (its own cap is 3 min);
   the adapter's shorter add timeout then fires as a client read timeout —
   which the generic transport handler mapped to `EngineUnavailable` →
   lane `unreachable`, telling the player the whole lane is dead when one
   torrent's swarm is. **Fixed** (`torrent_engine.py`): a read timeout on
   the add call now raises `EngineRejected` → provider `not_found` —
   "this item has no usable swarm", never "the lane is down". Pinned by
   `test_bitplay_add_read_timeout_is_dead_torrent_rejected` alongside the
   existing 504 test; full suite 1612 green, mypy strict clean.
2. **The live case that motivated it:** Sintel's fork-mirror pick
   (`A779FA75…`, 11 *claimed* seeds) produced no metadata for ~90 minutes
   across three add attempts — then recovered and streamed fine. Mirror
   seed counts lag reality; the 120 s verdict must be an honest item-level
   "not now", which is exactly what ships now.
3. **The real client flow has a detail step the old probe skipped:**
   search returns a group key; PlaybackInfo on the group key →
   `not_found`. The playable id (`yts:<imdb>:__movie__`) comes from the
   group detail envelope requested **with `?source=yts`**. The acceptance
   script now walks search → detail → PlaybackInfo, like Switchfin does.
4. **The server-side policy pick works as designed on live data:**
   Inception's mirror listing picked the 1080p entry (tier order, then
   seeds) and that swarm streamed immediately — one magnet, no fallback
   chain, per spec #374.
5. **Engine truth flows through the whole surface:** container learned
   from the engine session, subtitle stream derived from the torrent's
   real `.srt` file, stream URL names the actual picked file index — the
   #375/#377/#378 contracts hold against the real engine, not just fakes.
